# 消息投递语义、顺序与断线重连

## 1. 标识与顺序

- 每条消息有两个标识：
  - `message_id`：全局唯一（`msg_<uuid>`），跨频道也不重复，客户端可用于全局去重。
  - `seq`：**频道内**单调递增整数（从 1 开始），由服务端在持有房间锁时分配。
- 服务端在单把 per-room 锁内完成"取号 → 落库 → 扇出"，因此即便大量玩家并发发言，
  同一频道的所有在线成员看到的也是**完全相同的 seq 序列**，无空洞、无乱序、无重复。
- 不同频道之间不保证相对顺序（也无此需求），仅按 `(channel_id, seq)` 各自有序。

## 2. 重复与乱序（客户端侧）

- 客户端可为消息带 `client_msg_id`（如本地 UUID）。服务端在频道内维护有界的
  `client_msg_id` 索引：
  - 相同 `client_msg_id` 的重复/重试发送**不会**分配新 seq、不会重复落库、
    **不会**再次广播；响应里返回原消息并标记 `deduped: true`。
  - 索引容量与消息保留窗口有界（见 [`configuration.md`](configuration.md)），
    超出保留窗口的旧键会被淘汰。
- 即使客户端因网络重试把同一个 `body` 多次发出，只要不带相同 `client_msg_id`，
  仍会被视为两条新消息（这是"至少一次 + 客户端去重"模型的预期行为）。
- 所谓"乱序到达"在服务端不会造成分歧：取号与广播在锁内按同一顺序发生；
  消息一经分配 seq 即固定，迟到/重试请求不会重排已有 seq。

## 3. 在线投递

- 仅频道**成员**且在房间内的在线连接收到实时 `message` 事件。
- 扇出使用每连接的**有界非阻塞队列**：队列满时该连接被判为慢消费者，
  服务端立即断开并把该玩家移出房间和所有频道，其他成员不受影响。
- 去重命中（`deduped`）的请求不重复广播。

## 4. 断线重连与离线回放

连接/重连成功后，服务端严格按以下顺序下发，保证客户端看到的状态连续可解释：

1. `connected`
2. **离线期间错过的 `message`**：对每个该玩家已加入的文本频道，取
   `seq > acked_seq` 的消息，按 `(channel_id, seq)` 排序后先入队；
3. `snapshot`：当前房间成员与所有频道（含语音参与者）的权威全量状态；
4. 此后才是正常的实时推送。

由于回放事件先于快照、也先于任何新的实时事件入队（全部在房间锁内完成），
重连客户端不会出现"先看到新消息、后补旧消息"的倒挂。

- 离线**宽限期**：断线后成员身份与频道订阅保留 `offline_grace_seconds`，
  期内重连视为回归（`presence.rejoined=true`），继续接收并回放。
- 超过宽限期仍未重连：玩家被移出房间与全部频道，并广播
  `room_member_left`（`reason="offline_grace_expired"`）。之后再连即新成员。
- **语音通话不随离线保留**：断线立即从 `voice_participants` 移除并通知其余人，
  重连后需要显式 `join_channel` 重新加入通话；频道成员身份本身仍在宽限期内保留。

## 5. 确认水位（ACK）与不重复投递

- 客户端处理完消息后发送 `{"type":"ack","channel_id":...,"seq":N}`。
- 服务端为每成员维护每频道 `acked_seq`，语义为**单调水位**：
  - 只有更大的 seq 会推进水位；迟到的、旧的 ACK 不会让水位回退。
  - 回放只取 `seq > acked_seq`，因此**已确认过的消息永不重复投递**。
- 这构成"服务端至少一次 + ACK 水位 + `message_id`/`client_msg_id` 去重"的
  组合语义：可能重复到达（未确认就断线），但客户端具备一切去重信息。
- 未发 ACK 也能正常收消息；ACK 只影响断线后的重放下界。
- 也可随时用 `fetch_history`（`after_seq`, `limit`）主动、幂等地按需补拉。

## 6. 消息保留

- 每频道只保留最近 `channel_message_retention` 条消息用于回放/补拉；
  单次回放/补拉最多返回 `replay_max_messages` 条。
- 超出窗口的历史无法回放（客户端应自行持久化已收消息）。
